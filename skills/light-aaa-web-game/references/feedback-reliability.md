# 可选案例：逐次射击的可见反馈

本文记录港口射击试作所用的检查。项目设计需要逐发反馈时，可在开发前把相应射击规则加入自己的预算。通用游戏的事件格式和测试方法见[验证规范](validation.md)。

## 这次案例说明了什么

BREAKWATER 的旧测试检查扣弹、命中、敌人血量，但没有检查弹道画面。代码使用 `THREE.Line` 的默认约 1 像素线、90 ms 生命周期，从相机附近而非实际枪口生成；这些都会增加反馈不明显的风险。仅凭源码不能确定用户每次缺失的唯一原因，必须在对应机位、质量和帧节奏下复现。

## 港口试作的反馈协议

给每个被玩法系统接受的动作分配 `shotId`，携带会话/重开编号以避免重用。区分 rejected 输入（冷却、换弹、空弹、暂停）并给玩家合适提示。

一个 accepted shot 统一触发扣弹/命中、后坐力、音频、枪口焰、弹道、命中/撞击。这次试作每枪都需要枪口焰和弹道；若采用现实主义的非逐发曳光方案，必须在设计阶段明确另一种可靠的每枪视觉反馈，不能在缺失后悄悄改验收。

事件被创建、对象 `visible=true`、`onBeforeRender` 被调用，都不等于玩家看到了效果。记录实际主相机渲染后的提交，排除阴影/反射相机；即使已提交，也还要检查最终画面里的遮挡、亮度和尺寸。音频用实际 AudioContext/播放节点记录，不能只在扣弹时增加“已播放”计数。

## 实现配方与不变量

- 命中射线从准星出发确定瞄准点，视觉弹道从武器实际世界空间枪口发出。再检测枪口到瞄准点的近距离遮挡，避免贴墙穿射和准星/弹道不一致。视图层武器与世界层特效要有明确坐标变换。
- 不依赖 WebGL 原生粗线支持。可用相机朝向的 quad/ribbon 或细圆柱；保证约定距离和分辨率下的屏幕宽度与对比。色调映射/Bloom 不得把效果抹掉或扩成遮挡目标的亮团。
- 分开模拟时间和可视提交生命周期：新效果先进入待提交队列；至少经过约定数量的主画面提交后才允许回收。默认两帧。长帧不得让刚生成的效果在首次绘制前过期。停在后台不积累需补播的闪光。
- 玩家关键反馈保留独立容量或优先级。池满时可回收已完整展示的旧效果，不能随机吞掉新枪。记录 dropped/reused 计数并测试超过容量 3 倍的射击。
- 复用必须重置 TTL、可见性、透明度、颜色、顶点、矩阵、包围体、深度状态、层、shotId 和提交计数。重开清空队列、时间戳、音频节点、输入与所有活跃效果。
- 低档可以关闭反射/AO/天气，保留清晰开火、命中、受击和目标反馈。镜头冲击可降低或关闭，信息反馈应保留。

## 动态验证矩阵

同一输入路径覆盖：单发、长按连射、松开、空弹、换弹前后、瞄准、明亮/暗背景、近墙、敌人遮挡、低/中档切换、暂停/失焦恢复、连续重开后的第一枪。通过正常输入产生动作，不调用 `shoot()` 直接伪造用户操作。

在 60/30/15 FPS 节奏和一次明显长帧下重复测试。帧限制只改变调度节奏，不替换真实游戏逻辑或用静态截图伪装渲染。软件 GPU 下记录实际表现，不声称是真实硬件帧率。池复用测试至少达到池容量 3 倍；完整验收至少收集 100 次 accepted shot。

该试作的旧版脚本使用 `schemaVersion: 2` 并返回以下数据：

```python
return {
  'checks': checks,                 # 真实键鼠/状态断言
  'feedback': {'shots': shots, 'renders': renders},
  'stability': stability_observations,
  'captures': [                    # 文件必须真实存在于 artifacts_dir
    {'id': 'primary_action', 'path': 'shot-before.png'},
    {'id': 'primary_action', 'path': 'shot-frame-1.png'},
    {'id': 'primary_action', 'path': 'shot-frame-2.png'}
  ]
}
```

新版诊断记录使用 `actions / actionId / expectedChannels`。要复现本试作的严格反馈覆盖，在新版预算中设置 `requiredChannels: ["muzzle", "tracer"]`、`minAcceptedActions: 100` 和 `effectPoolReuseFactor: 3`（此项位于 `stabilityTargets`）；将上文的观测分别写入对应字段。`feedback_audit.py` 按预算计算 `缺失反馈对数 / 必需的 shot-channel 对数`、首帧延迟、独立提交帧数；没有样本即未验证。禁止从 shots 计数反推 renders，或把阴影 pass 当作玩家看到的帧。

连续短特效不能用“开枪后等 200 ms 再截图”验证。可在同一生产代码路径下用可控帧推进逐帧捕获最终画布，或录制足够帧率的视频；测试模式只允许控制时间、夹具和观察，不得把效果加粗/加亮/延长后冒充正式效果。另做不控制时间的实时试玩，防止测试路径掩盖问题。

`primary_action`、`reload`、`hit_and_damage`、`restart_and_quality` 是本案例使用的动态片段，各保留一段视频或至少三个连续关键帧并实际查看。ROI 像素差可以辅助判断有没有变化，但背景运动、粒子和后坐力也会改变像素，不能单凭像素差认证弹道可见。主画面提交审计和真实画面审查必须同时成立。
