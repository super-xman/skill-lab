# 从玩家目标到持续改进

## 先定义玩家要完成的事情

从用户指定的玩法和输入方式出发，把技术目标翻译成玩家能观察到的结果。

| 玩家阶段 | 玩家问题 | 设计要求 | 验收证据 |
|---|---|---|---|
| 首次进入 | 我在等什么，能开始了吗？ | 真实生成进度、明确开始按钮、必要键位与目标 | 冷启动记录；从正常入口到可操作的过程 |
| 第一次行动 | 我的操作生效了吗？ | 接受、拒绝和操作结果清晰可辨 | 真实输入、规则状态和连续画面 |
| 追踪目标 | 下一步有什么可做？ | 可操作对象、目标条件和进度清楚 | 新手从正常入口发现并完成一个目标 |
| 调整策略 | 为什么发生变化，接下来怎样应对？ | 可见线索与规则一致 | 改变一次输入，比较前后结果 |
| 恢复 | 如何从失误或中断中继续？ | 按玩法提供撤销、重新尝试或恢复入口 | 多次恢复后首个动作及状态正常 |
| 持续游玩 | 我还舒服吗，内容有变化吗？ | 输入、镜头、声音及节奏适合目标玩家 | 持续试玩并记录混乱、疲劳及重复点 |

`experience-plan.json` 在开发前记录玩家群体、设备、任务、成功标准及参考锚点。数字目标是本次设计目标，不是“已经测得”：例如 10 秒找到开始按钮，30 秒理解首个目标，只能通过相应观察确认。自动脚本按已知流程点按钮，不能代表新玩家自己理解了界面。

## 三种证据分别标记

- `measured`：浏览器实际记录的耗时、任务状态、帧、网络和资源数据。
- `agent_playtest`：用正常入口操作并看画面得到的体验评审；明确它是评审判断。
- `user_feedback`：用户实际说的体验；保留原话/来源、设备和能否复现。没有设备信息就写未知。

不要把一条用户反馈推成用户群体统计，不把自动化成功率称为玩家满意度。不能假装做过用户访谈。缺少真人研究不阻止已有范围内的修复与启发式试玩，但报告必须写明研究边界。

## 质量锚点先做样板

选 3–5 个对玩家最有感的参考特征，每个特征写“为什么重要、看哪个位置、怎样判断不足”。例如驾驶中弯道远景的可读距离，或解谜时旋钮的朝向与刻度。

先做一个可玩小场景：一个玩家会反复操作的对象、它在世界中引起的变化、一段可以完成的目标流程。保存基础光照、材质、接触/反射、最终后期的视图。近景和运动审查没过，不批量铺地图。优先减少关卡规模，不能删掉关键反馈换取“小包体”。

每轮继续对照用户的参考，不只与自己的上一版比较。独立场景不算像素复刻；比较尺度、明暗层次、材质区分、细节密度和玩家可读性。SSIM/PSNR 不适用于不同机位/布局的画质评分。

## 问题分级与建议

- P0：无法开始/完成、崩溃、丢失控制、核心数据损坏；先恢复可玩。
- P1：频繁或偶发地破坏核心体验，例如落位结果不可见、恢复后首个输入失效、指示与规则不一致；阻止验收。
- P2：不阻塞但明显影响质感、舒适和节奏，例如材质单薄、镜头晃动过大、提示遮挡操作对象。
- P3：可选扩展或低影响润色。

同级优先“高影响 × 高频 × 高证据置信度 ÷ 修改成本”。分数只是排序辅助，不能用低复现率把 P0/P1 降级。用户报告的核心问题未复现时保留待定位，不直接关闭。

每轮给出 2–3 条具体建议，使用这个格式：

> 在【玩家情境】中，【可观察问题】造成【玩家损失】。建议【最小改动】；预期【玩家结果】，用【实际测量/试玩证据】验收，同时回归【可能受影响的体验】。

例如，拼图旋转后方向标记被高光遮住，玩家会重复转动。调整标记对比度，比较同一机位的连续旋转画面，并回归撤销和低画质。

## 每轮的闭环步骤

1. **观察**：从正常开始入口试玩，先不调用定位夹具。记录玩家意图、操作、期望、实际结果与证据。夹具用于随后复现和归因，不能代替自然流程。
2. **建立假设**：一条问题配一个能被推翻的原因假设。例如“状态更新过早结束”与“已绘制但被界面遮住”应分开验证。
3. **建立失败回归**：先证明测试能发现问题，保留失败日志/画面。没有复现就不声称找到了根因；可以继续缩小条件。
4. **小范围修改**：一次改变一个主要因素，保持相机、输入序列、种子、质量和曝光可比。复用验证过的生成器/反馈组件；不要一次重写渲染和玩法。
5. **复测**：对比同一指标的 before/after，明确分母。例如 `缺失反馈数 / 已接受的核心操作数`，单独记录被规则拒绝的输入。
6. **回归**：至少检查核心流程、低画质、遮挡、重开、输入恢复和零网络请求。连续重开后对象池/监听器/声音不能增长。验证失败就返回假设步骤。
7. **沉淀**：关闭问题需要证据与回归通过；写入原因、修复策略和可复用规则。把偶发问题变成永久测试用例，避免下次生成重犯。

每轮都更新 `iteration-log.json`，记录当前构建哈希。优化结果只能属于被测试的那个 HTML。没有改善或引入新问题时保留失败记录、调整假设或撤回本轮改动。

## 收敛与再开启

交付条件：全部 P0/P1 关闭且有证据；核心体验评审通过；每个约定视觉维度达到目标；数值硬门槛满足；完整流程与修复后的回归成立。随机/时序问题至少在两个独立会话复测。P2 如果属于约定参考品质，也必须达到目标，不能靠换标签绕过验收。

没有真实 GPU 时，功能和画面可以继续迭代，硬件指标保留未验证；没有真人研究时，明确是体验评审。不要无限重复没有新假设的测试。受硬件/工具限制时给出可复现证据、已完成改进与剩余条件，不宣布全面通过。

用户的新反馈进入同一台账：重新打开相关问题，补充触发条件，复验后再关闭。Skill 本身也随失败案例更新规范与测试，形成“产出 → 玩家体验 → 失败用例 → Skill 修订 → 下一次产出”的闭环。
