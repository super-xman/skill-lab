# 实作反馈：BREAKWATER 港口试作

本 Skill 在一次独立港口 FPS 制作中实际运行。结论：能够指导形成自包含、程序生成素材、具有任务闭环的轻量原型，但仅列出技术路线不能保证参考 Demo 的视觉完成度。高画质要求还依赖成熟生成器、细节预算和多轮美术调校。

## 本次暴露的具体问题

1. 程序化锈迹最初形成大块迷彩斑。必须验证噪声的物理尺度、覆盖率和方向性：远处结构、表面污渍、微小颗粒分开；不要把一个阈值噪声铺在所有金属上。金属、涂漆和橡胶应有不同生成配方。
2. 每张标牌各造材质导致 draw calls 超预算。相同文字/样式缓存，独特文字进图集；按空间区域合批，避免丢失裁剪能力。
3. 一个目标点与路障重叠。路径审计必须检查玩家实际可站的交互位置，而不只是目标物体的几何中心。
4. 雨和镜面水洼出现在有屋顶的仓库里。统一室内遮罩，覆盖雨、湿润程度、反射和声音；不能分别调效果而忽略场景一致性。
5. 重开清零模拟时间后，旧的开火时间戳使武器暂时无法开火。重置所有基于时间的状态、输入、后坐力、队列和对象池，不只重置血量弹药。
6. HTML 拼装时，JavaScript `String.replace(marker, bundleString)` 会解释 bundle 中的 `$&`、`$\``、`$'` 等替换模式，破坏最终脚本。使用 `replace(marker, () => bundleString)`；对最终 HTML 中实际嵌入的脚本做语法检查，并重新打开成品验证。
7. 软件渲染使按模拟时间等待的测试显著变慢。固定质量的画面/性能验证与低分辨率的功能测试分开，并记录各自配置；不要把低档的速度算作中档性能。
8. Pointer Lock 会影响自动化点击设置按钮。测试应显式解除锁定，正常用户流程也必须能通过 Esc/P 暂停并操作菜单。

## 港口射击试作的视觉复测要点

- 初版总览一旦与参考显著不同，不得靠增大 Bloom、反射或噪点掩盖；明确是构图、光照、几何还是材质的问题。
- 保存同一机位的基础光照、完整材质、反射和最终后期视图，解释每一步的收益。
- 近景武器至少检查轮廓、倒角高光、不同表面粗糙度、螺钉/导轨尺度、瞄具和手部动作；全枪整体摆动不等于完整换弹动画。
- 道路至少区分干、潮湿和积水，具有非均匀磨损、标线磨耗、接缝与接触细节；整个地面像镜子不是目标。
- 用四个真实视角审查；能运行、数值没有 NaN、平均帧率达标，都不能替代视觉通过。

本次试作的具体截图和报告随游戏项目交付；不把未达标的原型截图当成后续项目的品质目标。

## 发布前迭代：来自真实体验的新反馈

用户确认视觉差距，并报告“有时候没有射击光线”。旧测试虽然验证了扣弹和伤害，却没有验证弹道是否进入最终画面；这是验收覆盖漏洞。单像素弹道、短生命周期、相机附近的起点及遮挡是需要排查的风险，不是已经证明的唯一根因。

因此把核心动作提交/可见性分开验收，增加时序、对象池、低档、重开与真实连续画面。网络验收从“能离线运行”提升为“入口之后任何额外请求尝试都失败”，覆盖同源、Worker、beacon、SW、资源提示和 CSP 拦截。

用户进一步要求从玩家角度提出改进建议并闭环迭代。因此增加体验计划、问题台账与修改前后/回归证据：每轮解释玩家损失、可证伪假设和可观察收益。规则更新本身不能关闭原游戏的问题，仍须对相同构建复测。
